# UI internationalisation

Deferred out of the feature port ([01-feature-inventory.md](01-feature-inventory.md))
and done afterwards, in three PRs.

| PR | What |
|---|---|
| #24 | The catalogue, and every composable reading from it |
| #25 | The view model's own messages, and the strings that were sitting in the platform entry points |
| #26 | The fifteen non-English locales |

## The catalogue

`shared/src/commonMain/kotlin/com/example/ui/i18n/Strings.kt` — a data class with
~120 fields, **each defaulted to the English text that used to be inline**.

That default is the design. A locale is a `Strings(...)` copy that overrides only what
it translates; anything it omits stays English rather than going blank. The source
material needed exactly that — the web build's own coverage is uneven
(`cameraTranslation` exists in 5 of its 13 locales).

A data class rather than a `Map<String, String>` because the field names are then
checked by the compiler: a renamed or deleted string breaks the build instead of
silently rendering an empty box at runtime.

Placeholders are `{0}` / `{1}`, substituted by `withArg` / `withArgs`. Not
`String.format` — Kotlin common has none.

## Where the locale comes from

`androidx.compose.ui.text.intl.Locale.current`, which is already multiplatform. So
there is **no new `AppContainer` member, no `expect`/`actual`, and nothing for either
platform to implement** — the seam the design would otherwise have required does not
exist because Compose already provides one.

`stringsFor()` strips the region (`pt-BR` → `pt`) and falls back to English.

Composables read `LocalStrings.current`. The view model cannot — it has no composable
scope — so it takes the catalogue as a constructor argument, and exposes it publicly
because the platform entry points show text outside the composition too (the
recognizer prompt, its failure messages).

## Deliberate decisions

1. **The device language picks the UI language, not the selected source language.**
   The web build does the latter (`getStr(sourceLanguage, key)`). Here the source can
   be `auto` — which has no strings — and users swap it constantly, so the UI would
   flip language mid-task. This is a deviation from the web build; it is recorded in
   `features/full-kmp-restructure/02-design.md` §8.
2. **Fifteen locales, not the web's thirteen.** Because the catalogue follows the
   device rather than the translation, it covers every language this app supports.
   Hindi, Dutch and Turkish had no web counterpart and were written from scratch.
3. **Language names are not translated.** `Language.name` also goes into the Gemini
   prompts, so it has to stay English. Translating the names in the picker is the
   separate "endonyms" item (Tier C, still out of scope).
4. **`Preset` lost its `label`.** The id stays — it is prompt text, product behavior —
   and the visible label is looked up by id in the catalogue, so each string has one
   home instead of two that can drift.
5. **Terms the web build already translated are copied verbatim** (tones, situations,
   the cultural warning, the rewrite actions), so the two builds speak with one voice.

## What the tests actually check

`shared/src/commonTest/kotlin/com/example/ui/i18n/StringsTest.kt`. The interesting
ones walk every shipped locale generically. Kotlin/Wasm has no reflection, so the walk
reads the data class's own `toString()`, splitting on a field boundary (`, name=`)
rather than on `", "` — the values are prose full of commas.

- **Every language the app can translate into has a catalogue.** Driven off
  `Language.supportedLanguages`, so adding a seventeenth language fails the build
  until someone writes its strings.
- **No locale drops a `{0}`.** Losing a placeholder in translation silently loses the
  language name it was meant to interpolate.
- **No locale uses a glyph the wasm canvas cannot draw** (`→`, `➔`, `·`) — the same
  constraint that put `extendedGlyphs` in `PlatformCapabilities`.
- **No locale leaves a field at the English default**, except an explicit allow-list of
  words that genuinely coincide ("Situation" in French and German, "Details" in German
  and Dutch, "Casual" in Spanish and Italian). The allow-list is the documentation of
  which ones those are.
- **No blank fields**, and a partial locale keeps English for what it omits.

## Roborazzi

English stayed the default and the screenshot tests run under an `en-US` Robolectric
locale, so **the baselines were never re-recorded** across all three PRs. The concern
recorded when i18n was deferred — "invalidates every Roborazzi baseline" — turned out
not to apply, precisely because English is the fallback rather than a locale like any
other.

## Owed manual check

The translations are machine-authored. Reading them on a device in a language the
owner speaks — Romanian is the obvious one — is worth doing before anyone else sees
them. Nothing in the suite can judge whether a string reads naturally.
